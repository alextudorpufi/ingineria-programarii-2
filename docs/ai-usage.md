# How we use AI

**Project:** Intelligent Services Marketplace (Ingineria Programării 2)
**Team:** Tudor Alexandru, Teodora Iacob, Sandu Theodor, Baltag Bianca
**Date:** 23 November 2026
**Status:** Description of our actual practice, with the evidence that supports each claim.

---

## 1. Summary

We use AI as an **implementation accelerator inside a process we control**, not as an author we delegate to.

- The AI agent works inside the repository, reads the code, and proposes changes; **a team member reviews, runs and merges** every change.
- Our standards are **committed to the repository** (`.agents/skills/`), not hidden in individual prompts, so every tool and every teammate gets the same rules.
- Every claim is **reproducible**: tests, CI workflows, migration checks and recorded command output. We do not accept "done" without evidence.
- We treat AI output as a **draft with a known failure mode**: it can look finished while doing nothing. The frontend examples in §10 are the clearest case.
- AI is **not used** for final architectural decisions, security sign-off, secrets, or anything we could not explain live during the demo.

---

## 2. Principles

Four rules drive everything below.

| # | Rule | What it means in practice |
| :-- | :--- | :--- |
| P1 | **The human owns the decision** | The agent may propose a design, but architecture, scope and merge approval stay with the team. |
| P2 | **Nothing counts until it is verified** | A change is complete only when the suite, the build and — where relevant — the running application agree. |
| P3 | **Nothing secret enters a prompt** | No `.env` values, tokens, signing keys, real user data or production credentials. `.env` is git-ignored and CI scans for leaks. |
| P4 | **We can explain every line** | If we cannot justify a change to the instructor or defend it in review, we do not keep it. |

## 3. The tools

| Tool | Role in our workflow | Where it lives |
| :--- | :--- | :--- |
| **OpenCode agent (LLM-backed)** | Reads the repository, plans, edits code, runs commands, drafts PR descriptions | Developer machines |
| **`code-skill`** | Engineering standard: module boundaries, persistence rules, clock, paging, migrations, testing, CI | `.agents/skills/code-skill/` |
| **`ui-skill`** | Design system: tokens, typography, component contracts, dark mode, responsive rules | `.agents/skills/ui-skill/` |
| **`frontend/AGENTS.md`** | Next.js-version-specific constraints and an agent feedback loop, generated by `next dev` | `frontend/AGENTS.md` |
| **CI: Backend Tests** | `./mvnw -B verify` on JDK 21 with Docker, so Testcontainers suites actually run | `.github/workflows/backend-tests.yml` |
| **CI: SonarQube** | Static analysis and duplication gate | `.github/workflows/sonar.yml` |
| **CI: Secrets Check** | gitleaks on every push/PR | `.github/workflows/secrets-check.yml` |
| **Repository docs** | The context we feed the agent: C4 diagrams, implementation plans, schema, previous verification reports | `docs/`, `README.md` |

Two deliberate choices here:

1. **The rules are versioned code.** `code-skill` and `ui-skill` are reviewed files in the repo. When the architecture changed, we updated the skill in its own PR (#12) instead of relying on memory or personal prompting habits.
2. **The gates are automated.** Because we let an agent write code, we invest in machine checks that do not care who wrote it: 241 tests, ArchUnit boundary rules, `ddl-auto: validate`, SonarQube and gitleaks.

## 4. The workflow we enforce

Every non-trivial task follows the same phases. This is written into `code-skill` as a mandatory lifecycle.

| Phase | AI does | Human does | Artefact |
| :--- | :--- | :--- | :--- |
| 1. Requirements | Restates scope, lists open questions, proposes the API contract | Decides scope, answers ambiguities | Issue / PR description |
| 2. Discovery | Searches the real module paths for existing models, ports, services, helpers | Confirms nothing is duplicated | Reuse list in the plan |
| 3. Plan | Writes files-to-change, ports, migration name, test strategy | Approves or corrects the plan | `docs/*-implementation-plan.md` or PR plan |
| 4. Data model | Drafts DDL, constraints, indexes; checks Flyway numbering | Approves the schema as a contract | Migration + `InitialSchemaMigrationTest` |
| 5. Implementation | Edits code layer by layer, small commits | Reads the diff | Commits |
| 6. Verification | Runs the suite, the build, the health check; reports exact output | Re-runs or spot-checks; rejects unverified claims | Command output in the PR |
| 7. Review | Drafts the PR body: problem, change, evidence, risks | Reviews, requests changes, merges | Merged PR |

The important inversion: **the plan and the acceptance criteria come before the code**, so "the AI wrote it" never becomes an excuse for not knowing what the change is supposed to do.

## 5. What we give the agent before it writes code

A vague prompt produces plausible-looking code that does not fit. We always supply:

1. **The applicable skill** — `code-skill` for backend, `ui-skill` for UI, both for full-stack work.
2. **The concrete target** — a numbered finding, a plan section, or a failing test, never "improve the app".
3. **The boundaries** — which module owns the change, what must not be touched (for example "do not edit `V0__initial_schema.sql`").
4. **The definition of done** — the exact commands and the expected observable result.
5. **Explicitly, the known traps** — `LocalDateTime.now()`, SQL `now()`, `findAll()` on user-facing lists, `save()` on a rebuilt entity, hardcoded enum strings.

### Prompt patterns that worked

| Pattern | Example |
| :--- | :--- |
| Numbered audit | "Review `marketplace-infrastructure` against these criteria; return numbered findings with severity and file:line. Do not change code yet." |
| One finding per change | "Implement I-7 only. Do not refactor neighbouring methods. Add the unit test that fails without the clamp." |
| Evidence demanded | "Show the command output. If something was skipped, say so." |
| Cause over symptom | "The test fails because the entity is rebuilt and loses `@Version`. Fix the write path, do not delete the assertion." |
| Ground the docs | "Before writing guidance, read the module tree and the current migration. Do not invent table or package names." |
| Explicit stop | "If the repository does not support this, say so instead of adding a speculative abstraction." |

### Prompt patterns that failed

| Pattern | What went wrong |
| :--- | :--- |
| "Make the app work" | Produced broad, unreviewable changes across layers. |
| "Add tests for this" with no rule | Generated tests that asserted the implementation rather than the requirement. |
| "Update the documentation" from memory | The first `code-skill` described `backend/src`, `pro_wallet` and `claimed_pros` — none of which exist. Fixed in #12 by reading the actual repo. |
| Accepting a summary without the diff | The summary described behaviour the code did not implement (see §10). |

## 6. Guardrails: from AI claim to verified fact

| Risk | Mechanism in this repository |
| :--- | :--- |
| Broken module boundaries | ArchUnit test (`CleanArchitectureTest`) fails the build on Spring/JPA imports in `domain`/`application` |
| Schema drift | Flyway owns the schema, `ddl-auto: validate` runs at startup, `InitialSchemaMigrationTest` pins the table set, seeds, defaults and CHECKs |
| Testing that never runs | CI runs `verify` with Docker; locally the suites skip and **say so** (`disabledWithoutDocker = true`) |
| Financial errors | `Credits` value object, append-only ledger, guarded native updates, optimistic locking with 409 |
| Secrets in the repo | gitleaks workflow; `.env` ignored; no development fallback for `JWT_SECRET` |
| Quality regressions | SonarQube workflow; duplication tracked (recorded as **0.0%** new duplicated lines on 2026-11-06) |
| Performance regressions | SQL statement analysis (commit `e9227a8`): JDBC counting plus AOP around controllers/services, slow-statement threshold, disabled in production by default |
| Unreviewed AI output | Every change lands through a PR with a body listing problem, change, verification and risks |

## 7. Case study: the hardening programme (PRs #8–#11)

Our largest AI-assisted effort was a **review-driven hardening pass**, module by module.

1. The agent audited one module against explicit criteria and produced **numbered findings** with severity: `H1–H3`, `M1–M10`, `L1–L11` for the application layer, `D1–D17` for the domain, `I-1–I-14` for the infrastructure.
2. We triaged: severity, effort, risk, and whether the finding was real. Several proposed changes were rejected as speculative.
3. Each fix was implemented with its own test and its own commit.
4. The PR body recorded the finding, the change, and the **verification output**.

The measurable result of that pass:

| PR | Scope | Files | Diff | Suite at the time |
| :--- | :--- | ---: | ---: | :--- |
| [#8](https://github.com/alextudorpufi/ingineria-programarii-2/pull/8) | Application layer policy | 35 | +489 / −163 | 86 tests |
| [#9](https://github.com/alextudorpufi/ingineria-programarii-2/pull/9) | Domain invariants | 99 | +1938 / −510 | 208 tests |
| [#10](https://github.com/alextudorpufi/ingineria-programarii-2/pull/10) | Persistence boundary | 61 | +1392 / −131 | 241 tests |
| [#11](https://github.com/alextudorpufi/ingineria-programarii-2/pull/11) | Migration consolidation | 14 | +321 / −428 | 241 tests, 0 skipped |

Today the repository contains **241 `@Test` methods**, and the promoted branch (#13) was 156 files, +5046 / −1505.

What AI was genuinely good at: mechanical breadth — finding every `LocalDateTime.now()` call site, renaming a port across layers, writing the 18 adapter tests, keeping 241 tests green through a refactor.
What it was not good at: deciding **whether** a finding was worth fixing, and judging which refactor was too large for the remaining time.

## 8. Case study: the migration consolidation (#11)

The project was unreleased, so eleven incremental migrations carried upgrade paths no database needed. We replaced them with a single `V0__initial_schema.sql`.

The risk was silent schema drift, so the acceptance criterion was not "it looks right" but a **reproducibility proof**:

1. Apply `V1`–`V11` to an empty PostgreSQL 18.
2. Write `V0` from the resulting catalog.
3. Apply `V0` to a second empty database.
4. Compare `pg_dump --schema-only` of both — **byte-identical**, with the same five seeded rows.

The human decision was *whether* to consolidate. The agent executed the mechanical comparison, and the proof made the result reviewable by someone who did not watch it happen. The migration test that depended on intermediate versions was replaced by `InitialSchemaMigrationTest`, which now pins the final contract so a future AI edit cannot quietly change the schema.

## 9. Case study: correcting the instructions (#12)

The first version of `code-skill` had been written from memory. It pointed at `backend/src`, referenced tables named `pro_wallet` and `claimed_pros`, and recommended a matching-strategy engine that does not exist.

That is the characteristic failure of AI-generated documentation: **it is fluent and wrong**. We fixed it the only reliable way — by reading the actual module tree, the actual migration and the actual tests, then rewriting the skill and marking unimplemented patterns explicitly as *future*.

The lesson generalises: when the agent's instructions rot, every downstream change inherits the rot. We now treat the skills as **code that must be kept in sync with the schema and the module layout**, and update them in their own reviewable PR.

## 10. Case study: the screen that lied

While planning role-based testing we inspected the frontend against the API. Several features *looked* complete in the browser:

- **Ratings** — the modal submits, the review appears in the profile, and the count increments. In reality `submitRating` only mutated React state (`AppContext.tsx`); nothing was sent to the backend, and the `ratings` table was never written.
- **Admin actions** — "approve lead" and "refund all" displayed a success message after a `setTimeout` and called no endpoint.
- **Client disputes** — the queue deliberately returned `[]` for clients, so the screen was empty by construction rather than by policy.
- **Chat** — the interface existed; there was no backend chat API.

None of this was a lie by the AI in the sense of fabrication; it was the natural result of generating UI before the contract existed. But a demo would have shown working features that did not work.

**Rule we took from it:** verify against the **network and the database**, not the screen. A feature counts when a request is sent, a row is written, and a reload still shows the result. This is why our role-area plan (ratings, administrator actions, support tickets) starts from endpoint and schema contracts, and why "can it be submitted?" is answered with a `curl` and a `SELECT`, not a screenshot.

## 12. What we do not use AI for

- **Final architecture or scope decisions.** The agent can enumerate trade-offs; the team chooses.
- **Security sign-off.** Authentication, authorization and payment handling are reviewed by a person against the threat model.
- **Secrets and personal data.** Never pasted into a prompt; `.env` stays local.
- **Invented results.** We do not report a test count, a benchmark or a "passing build" we did not observe. When the suite skipped integration tests, the report said so.
- **Writing the demo explanation.** Every member can walk through their own code.

## 13. Academic integrity and attribution

- AI output is **not submitted as authored work without review**; it is a tool comparable to a compiler, a linter or an IDE refactoring, used under the same obligation of understanding.
- We record **what was AI-assisted** at the level that matters for review: the PR history, the findings, and the verification evidence are all in the repository and reproducible.
- External sources are cited where used: the project proposal, framework documentation, and the Next.js agent guidance shipped in `frontend/AGENTS.md`.
- **No fabricated data.** Seed data is generated and labelled as such; screenshots are not used as proof of behaviour.

## 14. Risks and mitigations

| Risk | Mitigation |
| :--- | :--- |
| Confident but wrong output | Every change is verified by a test, a build or a live check; unverified claims are rejected in review |
| Plausible UI without a backend | Contract-first planning; verify with a request and a database read (§10) |
| Architecture erosion | `code-skill` boundaries + ArchUnit + a documented module map |
| Stale instructions | Skills are versioned and corrected in review (#12) |
| Over-generation / scope creep | YAGNI rule in the skill; findings are triaged before implementation; no speculative tables, ports or patterns |
| Secret leakage | gitleaks workflow, ignored `.env`, no development JWT fallback |
| Loss of understanding | Small commits, PR bodies written for a human reader, live explanation in the demo |
| Cost and noise | One task per prompt, plan before code, prefer reading the repo over guessing |

### Reproduce the checks

```bash
# Backend suite (needs Docker for the Testcontainers suites)
cd backend && ./mvnw -B clean test

# Frontend
cd frontend && npm run lint && npm run build

# Schema and startup validation
docker compose down --volumes && docker compose up -d db backend
docker exec -it marketplace-db psql -U "$DB_USER" -d "$DB_NAME" \
  -c "SELECT version, description, success FROM flyway_schema_history;"
```

Expected: 241 tests with 0 failures, a clean frontend build, one Flyway history row (version `0`, success), and a healthy backend — which is only reported as healthy after Hibernate has validated the schema against `V0`.
